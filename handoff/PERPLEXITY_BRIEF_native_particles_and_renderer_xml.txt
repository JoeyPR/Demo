4. NEW FINDINGS FROM THE RUNTIME CODE REVIEW (src/xml-renderer.mjs, 328 lines)  [VERIFIED by reading]
====================================================================================================
4.1  Only 5 scripts get XML sprite rendering
  advanceXmlRenderer replaces catalog pieces with SpriteRender rules ONLY for AURA_RULES =
  StarryAura, DirtAura, TwilightAura, InfinityAura, BeachAura. The other ~309 scripts keep captured
  stills and only add particle runs. So 928 SpriteRender nodes are essentially unexecuted outside
  five items.
4.2  Particle space is hard-wired to the body
  spritePiece() always emits attachment 'body' at x=16+offset, y=32+offset with anchor (.5,.5).
  There is no hand-spot, world-space, or target-space path, and renderAlignment (125 uses) is
  ignored.
4.3  Dead code vs missing code
    Implemented but 0 uses in any XML:   <Sin>, <Cos> (property()), SpriteScaleAnimation, SpritePositionAnimation (advanceXmlRenderer).
    Used in XML but not executed:        SpriteCurveAnimation 133 | SpriteSinPulseAnimation 49 (Parameter pos.y with Set period/scale, e.g.
                                         AngelAndDevil float) | CurveAnimationFloat 23 / Vec2 2 / Vec3 16 / Vec4 18 | InterpolationFloat 36 /
                                         Vec2 20 / Vec3 19 / Vec4 57 | SequenceAnimation 15 | DelayAnimation 14 | VisibilityAnimation 5 |
                                         playOnAction (SpriteAnimation 44, SpriteCurveAnimation 4, SpriteSinPulseAnimation 4, SequenceAnimation 1, VisibilityAnimation 1) | useFacing on curve animations (10+6+6).
    The sprite-motion side of the XML (floating angels, pulsing glows) is therefore not just a particle problem.
4.4  Event hooks are not gated
  visibleRules() iterates every child of <RenderRules> with no regard to which event the hook
  represents. A ParticleSystem rule inside OnDamagedTile (62 hooks), OnDestroyedTile (53),
  OnPunchStart (52), OnKilled (3), OnRespawned (6), OnEnteredToWorld (3) is therefore treated like a
  steady-state rule and is only filtered by its own onState/onAction. [UNVERIFIED in the browser:
  reproduce with one OnDamagedTile item and confirm; if it fires continuously it is a bug.]
4.5  Silent failure path
  When a particle property evaluates to NaN (e.g. RandomRadial initialVelocity, Multiply offset),
  the particle is skipped and the system name is added to item.xmlUnsupportedParticleExpressions.
  That is fail-closed, which is correct, but 159 RandomRadial uses means a large share of systems
  are being dropped entirely. Surface this set in the UI/coverage report instead of leaving it
  buried.
4.6  Randomness and bounds
  Seed = (emission*31 + k*17 + item.id); replay window 96 emissions, 256 particle calls per result,
  128 runs / 10 s retained. Fine for deterministic tests; it cannot reproduce native emission
  history and it truncates long-lived or infinite systems (infLifeTime is 'true' in 376 of 397
  emitters that set it). Document this as a known deviation.
4.7  Conditions and variables
  condition() knows variables speed.x, speed.y, speed.length, onGround, punchInProgress, punching,
  isFacingLeft only; ITEM_SYMBOL_IDS has 6 entries. Unknown things return undefined and visibleRules
  treats StopIf(undefined) as 'stop'. Uses in data that are never evaluated: CompareCustomVariable
  129, ArithmethicOperation 250, ItemHasTag 20, IsAnimationFinished 23, IsHoldingJumpKey 4,
  IsDarkTile 4, CheckRandomRangeNumber 5, RandomValueOperation 3, SetVar 14, VariableMap 109,
  Parameter 49. 'custom variables' drive LineRender (BalloonBackpack) and many state transitions;
  expect silent wrong states.
4.8  RenderOptions are almost entirely ignored
  Only ShouldHover is consumed (motion-policy.mjs). See section 6 for the other ~45 flags, several
  of which are native layering/hiding/behavior rules.

6.1  Atlas / sprite addressing  [EVIDENCE - strong]
    <Sprite name fileName textureSize frame> : fileName 'game/particles11.rttex' -> assets/game/particles11.png.
    textureSize = ONE cell size ('32', '64') or 'w,h' ('64,64'). frame = 'col,row' CELL INDEX (not pixels); some frame values have spaces
    ('10, 13'); some are empty (282 particles11 sprites) -> treat empty as 0,0 and log. Pixel rect = (col*w, row*h, w, h).
    Proof: the seven differing sprites land exactly on 32/64-px cell boundaries (480=15*32, 704=22*32, 640=10*64, ...). SpriteAnimation <Frame>c,r</Frame>
    uses the same cell indices. 8 Sprites use `fname`/`scale` instead of fileName/frame (parse them).
6.2  Units  [EVIDENCE for degrees and normalised curves; HYPOTHESIS elsewhere]
    * Particle <Curve> keyframes are x=NORMALISED AGE: 1,042 of 1,048 particle curves end at exactly 1.0. So Curve(time) -> age/lifeTime.
    * Angles are DEGREES: initialAngle values are 0..360 (146), -360..360 (10), 90 (29), -75..75 (9); RandomRadial angleRange 0,360 / 230,310;
      initialRotationRate 5..15, 360, -300..300 -> deg/s.
    * lifeTime, emissionInterval, delayTimer, Emitter lifeTime: SECONDS (e.g. 0.05, 0.8, 1). OrbitOffset periods/time offsets: MILLISECONDS (6000, 4000, 500).
      Particle-level orbitPeriod is SECONDS (3). Mixed units are real; do not 'normalise' them by assumption.
    * Velocities / offsets / amplitudes: pixels in the item's authored 32-px-tile space [HYPOTHESIS: px/s and px; confirm one item].
    * Angle origin and direction for RandomRadial (0 = +x? clockwise or counter-clockwise on a y-down screen?) [UNKNOWN] - InfinityAura angleRange
      230..310 with velocity radius 150..200 looks like an upward fan on a y-down screen, which suggests 0 = +x, increasing clockwise-on-screen. Verify.

6.6  Blend modes  [VERIFIED data / HYPOTHESIS meaning]
    Counts: PREMULTIPLIED_ALPHA 613 particles (+452 SpriteRender), ADDITIVE 225 (+26), PREMULTIPLIED_NORMAL 1, NORMAL 52 (SpriteRender).
    DATA FACT: the shipped atlas PNGs are STRAIGHT alpha, not premultiplied: in particles11/12/large17 and player_cosmetics4 only 8-24% of semi-transparent
    pixels satisfy max(rgb) <= alpha (a premultiplied image would be ~100%); typical rgb/alpha ratio is 7-21x (bright color at low alpha).
    So 'PREMULTIPLIED_ALPHA' is a draw-time choice and the engine either (A) premultiplies the texture at load, giving ordinary-looking soft edges, or
